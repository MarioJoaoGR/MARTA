Diagrama da ferramenta: Python vs Ruby

O mesmo pipeline nas duas versões. Dentro de cada caixa, PY é a original, RB o porte.

1O que o Prism faz, exatamente

Sim, é isso: o Prism constrói uma árvore de sintaxe do código Ruby, tal como o ast faz para Python. Mesma ideia, mesmo papel no pipeline.

A diferença está em onde essa árvore existe.

  • Python: o ast é da própria linguagem. Corremos em Python, a árvore fica em memória como objetos Python, e usamo-la diretamente.
  • Ruby: o Prism é uma biblioteca de Ruby e produz a árvore como objetos Ruby, dentro do processo Ruby. A nossa ferramenta é Python. Objetos Ruby em memória não são acessíveis do Python: são dois interpretadores diferentes, com representações de memória diferentes.

Por isso o marta_parse.rb faz três coisas:

  1. pede ao Prism a árvore do ficheiro;
  2. percorre essa árvore e extrai só o que nos interessa: classes, módulos, métodos com os respetivos intervalos de linhas, tipos de parâmetros, chamadas (com a forma do recetor) e atributos;
  3. escreve esse resumo em JSON no stdout.

O JSON é a ponte: um formato de texto que as duas linguagens sabem ler e que atravessa a fronteira entre processos. Do lado Python só falta convertê-lo nas nossas estruturas (MethodInfo, ClassInfo, FileParse).

Nota: não atravessamos a árvore inteira, só o resumo. Enviar tudo daria um JSON enorme e uma conversão lenta, sem ganho nenhum.

2O grafo de chamadas: a ferramenta que tivemos de construir

Para que serve: saber quem chama quem. Quando geramos testes para o método X, o contexto que damos ao modelo inclui o que o X chama por dentro, e propaga a intenção (o que falta testar) do chamador para os chamados. Sem grafo, cada método é uma ilha.

Em Python isto está resolvido: existe o PyCG, uma ferramenta publicada (ICSE 2021). Em Ruby não existe nada equivalente. Foi preciso construir.

Como foi feito, por etapas

  1. O parser regista a forma do recetor. Em cada chamada, o marta_parse.rb não guarda só o nome do método invocado. Guarda também sobre quem foi invocado: nada, self, uma constante, uma variável local, uma variável de instância, self.class, ou um getter. Esta classificação é o que torna a resolução possível.
  2. O resolver liga cada chamada a um método concreto, usando:
    • a ordem real de procura do Ruby (prepend → a própria classe → include → superclasse);
    • duck typing: se dentro do corpo se faz x.upcase, infere-se o que x é pelos métodos que lhe são chamados;
    • colaboradores guardados em variáveis de instância e expostos por attr_reader;
    • casos particulares do Ruby: self.class.new e os métodos de classe declarados dentro de class << self.
  3. Construímos um segundo grafo para poder medir o primeiro. Usando TracePoint, que observa as chamadas reais durante a execução, gerámos o grafo dinâmico da gem money a partir da suite de testes dela. Esse grafo nunca entra na ferramenta: serve só de instrumento de medição, como uma régua.
  4. Medimos, corrigimos, voltámos a medir. A primeira versão acertava 35,9% das chamadas reais. Três correções dirigidas (class << self, colaboradores por variável de instância, e self.class.new) levaram-na a 49,6%.

Ainda pode ser otimizada?

Sim, mas convém separar o que é teto do que é trabalho por fazer.

  • Teto real (nenhuma análise estática resolve): despacho verdadeiramente dinâmico: send, method_missing, define_method. O nome do método só existe em tempo de execução. O PyCG tem exatamente a mesma limitação em Python, não é fraqueza do nosso.
  • Alcançável com mais trabalho: blocos e procs passados como argumento, e chamadas que saem para dentro das dependências (hoje só indexamos o código do próprio projeto).

A dizer antes que perguntem: os 49,6% foram medidos numa única gem, a money. É um número honesto e obtido com instrumento próprio, mas ainda não é um número geral. Para o paper tem de ser medido em mais projetos do corpus. Comparação de referência: o PyCG publica cerca de 69,9% de recall.

3Contexto de tipos: anotações e uso

Python pode ter anotações de tipo (def add(a: int, b: int)), embora não sejam obrigatórias: quem escreve o código decide se as põe. Quando existem, dizem-nos o tipo diretamente.

Em Ruby não existem anotações de tipo, de todo. Por isso trabalhamos apenas com o uso: olhamos para o que é feito ao parâmetro dentro do método. Se o corpo faz a.strip, então a comporta-se como texto.

4O que é o RSpec

É o framework de testes dominante em Ruby, o papel que o pytest tem em Python. Os testes escrevem-se em blocos que se leem quase como inglês:

require "calc"

RSpec.describe Calc do
  it "soma dois números" do
    expect(Calc.new.add(2, 3)).to eq(5)
  end
end
  • describe e context agrupam;
  • it é um caso de teste, a unidade que conta;
  • expect(...).to eq(...) é a asserção.

5O que é pedido nos prompts

Planner, desenha o plano, não escreve código

Recebe o código do método mais o contexto da Fase 1, e devolve uma lista JSON de cenários, sem uma linha de Ruby. É-lhe pedido:

  • três cenários distintos: caminho feliz, casos-limite (nil, listas vazias, fronteiras) e entradas inválidas ou erros esperados;
  • se o contexto trouxer linhas por cobrir (vindas do ciclo externo), tem obrigatoriamente de desenhar os cenários para executar essas linhas;
  • preferir objetos reais com valores simples no setup, e só sugerir doubles para entrada/saída externa verdadeira;
  • devolver só JSON, sem Markdown nem explicações.

Dev / Assertion, transforma o plano em código executável

Recebe os cenários e o código do método. As regras mais importantes:

  • devolver só um bloco de Ruby, ficheiro completo e autossuficiente, a começar pelo require certo;
  • um bloco it independente por cenário;
  • evitar mocks: nunca simular a classe sob teste nem objetos que se possam instanciar; só isolar entrada/saída externa. Um double mal posto faz o teste passar sem testar nada;
  • nunca redefinir constantes globais nem fazer monkey-patching;
  • 1 a 2 expect por bloco, com valores concretos deduzidos do código-fonte. Vários blocos pequenos são preferíveis a um bloco com muitas asserções, porque basta uma errada para matar o exemplo inteiro.

Na reparação o prompt muda, passando a incluir a mensagem de erro da tentativa anterior e exemplos de métodos semanticamente próximos desse erro, procurados no índice RAG.

6O rspec -f json

-f json escolhe o formato da saída. Em vez de pontos e texto colorido feitos para humanos, o RSpec devolve os resultados em JSON: um registo por teste, com o estado, a mensagem de erro e a linha onde falhou.

Serve para recebermos os dados no mesmo formato em que já os recebíamos em Python (lá é o pytest --json-report). Assim o resto da ferramenta não muda: trata os dois da mesma maneira.

Juntamos ainda -O /dev/null, que manda ignorar o ficheiro .rspec do projeto. Os nossos specs são autossuficientes e não devem herdar configuração de quem estamos a medir.

7coverage.py e o Coverage do Ruby

PythonRuby
O que é Biblioteca externa, madura, instalada à parte Módulo embutido no interpretador, nada para instalar
O que devolve Linhas e ramos, com API para consultar regiões Por ficheiro, um array indexado por linha com o número de execuções (vazio se a linha não for executável)

A diferença que importa: o Ruby dá-nos a informação por ficheiro. Mas o ciclo externo precisa das linhas em falta por método, para poder dizer ao Planner "cobre as linhas 12 a 15". Por isso sintetizamos: cruzamos o intervalo de linhas de cada método, que o parser já nos deu, com o array de execuções.

O que é preciso vigiar

Essa síntese vale o que valem os intervalos de linhas do parser. Na prática: perguntamos "onde começa e onde acaba o método X", recebemos por exemplo "linhas 40 a 52", e marcamos como em falta as linhas desse intervalo com zero execuções. Isto assume que o código do método vive mesmo entre essas duas linhas. Falha quando:

  • o método é criado por metaprogramação (define_method): não há corpo literal no ficheiro naquelas linhas;
  • o método é de uma só linha (def add(a, b) = a + b): não há como distinguir coberto de parcialmente coberto;
  • o código está dentro de um bloco passado a outro método, e pode ser atribuído à linha de fora.

Nestes casos o número daquele método pode ser otimista ou pessimista. O total do projeto não fica errado, porque vem das linhas em bruto, mas o ciclo externo pode ser mal orientado: dizemos ao Planner "cobre a linha 45" quando não é a linha 45 que falta.

Vamos ter cobertura de linhas e de ramos em Ruby?

Recolhemos as duas. O Coverage.start(lines: true, branches: true) já pede ambas ao interpretador.

Lacuna conhecida: o nosso emissor de JSON só escreve as linhas. Os ramos estão a ser recolhidos e deitados fora. Isto tem consequência direta: os resultados do Python reportam linhas e ramos combinados, por isso enquanto o Ruby só usar linhas as duas séries não são comparáveis nessa métrica. A correção é pequena (emitir também os ramos e usá-los na síntese) mas ainda não está feita. É a lacuna mais relevante do lado da medição.

8Salvamento e rondas de geração

O salvamento é funcionamento normal, sem nada de especial: se um ficheiro tem 5 testes e 2 falham, em vez de descartar o ficheiro inteiro cortam-se só os 2 blocos que falharam, limpa-se o que ficou vazio, verifica-se a sintaxe e corre-se outra vez.

Como funcionam as três rondas

Ronda 1: gera para todos os métodos-alvo. No fim, mede a cobertura de tudo o que existe em disco.

Rondas 2 e 3: por cada método, olha para o resultado da medição.

  • Se o método ficou totalmente coberto, é saltado. Não se gasta mais orçamento de LLM nele.
  • Se ficaram linhas por cobrir, gera um ficheiro novo para o mesmo método, e o prompt do Planner passa a incluir a lista dessas linhas, com instrução explícita para desenhar os cenários que as executam. O ficheiro novo acresce aos anteriores, não os substitui.

Respondendo ao teu cenário: se na ronda 1 só passou o caso do caminho feliz, o método não está totalmente coberto. Logo nas rondas 2 e 3 ele volta a ser tentado, agora com as linhas que faltam indicadas no prompt. Só é saltado quando chega aos 100%.

É por isso que o número de ficheiros por método varia: os métodos fáceis ficam com um, os difíceis podem acabar com três.
